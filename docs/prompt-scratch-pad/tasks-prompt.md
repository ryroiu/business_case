# Task drafting brief — Signpost

After the plan is drafted and checked, derive a proposed `docs/design/tasks.md` from it and specification v0.2. Follow the downloaded tasks template and guide. Keep the course's five-column task list and unchanged Definition of Done.

Inspect the existing prototype so tasks do not order a duplicate rebuild. Use small acceptance/refinement steps tied to actual files. Start every task with an action, assign a stable T-number, trace it to requirements or ADRs, and name its dependencies. Keep each task below one working day and define an observable pass condition. Fix existing code only if the corresponding check identifies a mismatch.

Cover data validation and retry, safe text/links, review-date rules, cards, combined filters, navigation, detail recovery, normal/failing pin storage, About/sample resources, keyboard access, responsive layout, and the two separate performance targets. Then prepare real-user evaluation and a reviewed release.

Distinguish code that exists from a new acceptance task that is not yet started. Existing AI-run browser checks do not satisfy the guide's human-review requirement. Do not mark tasks Done without passing evidence and human review. Log participant availability and plan sign-off honestly. Treat this as a proposed backlog while human approval is pending, not as permission to execute it.
